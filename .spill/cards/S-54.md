## Purpose
When a flow breaks (a button that does nothing, an approve that fails, a tool call refused), there is nothing to inspect afterwards. events.jsonl records only what succeeded, the app sends the board server's output nowhere, and errors shown in the UI are gone once the sheet closes. Spill should keep a diagnostic log per project so the user and Claude can see what failed and why.

## Requirements
1. Each project has a diagnostic log under the user's home folder, `~/.spill/logs/<project>-<short hash of its folder>.log`, not in `.spill/`, so it is never committed. One JSON line per entry: time, source (server, ui, mcp, app), level (error, warn, info), what (route, tool or action), card if any, and message.
2. The board server logs every API request that fails (status 4xx or 5xx) with its route, card and error text, and any uncaught error with its stack.
3. The MCP server logs every tool call that returns an error, with the tool name, its arguments (long text cut to 200 characters) and the error.
4. The board page sends its errors to the server for the log: uncaught exceptions, failed fetches, and every error message it shows the user (the red text under a card's buttons, failed answers, failed comments).
5. The board page also logs, at info level, when the user presses a button that is disabled, with the button and the reason it is disabled (its tooltip). This catches the case where nothing visibly happens.
6. The desktop app writes each board server's output (stdout and stderr) to the same log, source "app", instead of discarding it, and logs a board server that exits unexpectedly.
7. The log keeps the last 2 MB: past that, the oldest half is dropped.
8. `spill logs` prints the current project's log, newest last; `spill logs --errors` shows only errors. A new MCP tool, spill_logs (optional limit and level), gives Claude the same, and the MCP instructions tell Claude to read it when the user reports something that did not work.
9. Nothing secret is logged: no file contents or design HTML, and text arguments are cut as in req 3.

## Out of scope
- A log viewer in the app UI.
- Sending logs anywhere off the machine.
- Logging successful actions (events.jsonl already has them).

## Acceptance checks
1. An approve refused by the server (open question) shows in `spill logs` with the route, card and error.
2. A failing MCP call (for example setting a spec active that is not queued) shows with the tool, arguments and error.
3. A click on a disabled Approve logs an info line with its reason.
4. An exception thrown in the board page reaches the log.
5. In the app, a board server's stderr lands in the log, and killing it logs an unexpected exit.
6. Writing past 2 MB keeps the file under 2 MB with the newest entries.
7. spill_logs returns the same entries as `spill logs`, filtered by level.
8. The log file is under ~/.spill/logs and nothing appears in `git status` for the project.
