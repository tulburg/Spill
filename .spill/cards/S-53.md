## Purpose
Cards drafted by mistake (a duplicate, or an update drafted as a new spec, like S-50 to S-52) can only be rejected today, which leaves them on the board. Let Claude delete a card, but only after the user agrees on the board.

## Requirements
1. A new MCP tool, spill_propose_delete (id, reason), creates a question "Delete S-n?" with the reason in its body and the options "A. Delete it" and "B. Keep it". The question is linked to the card.
2. Only cards with no code behind them can be proposed: specs in draft, discussing, approved or rejected, and questions that are open or dropped. A done spec is refused with a pointer to spill_propose_replace; active and queued specs are refused.
3. Answering A deletes the card: its file is removed, every link to it on other cards is removed, and its open questions that block nothing else are deleted with it. The deletion is logged as an event ("deleted S-n: reason") and reaches Claude's inbox. The question itself stays, answered, as the record.
4. Answering B keeps the card; Claude does not propose it again unless something changes.
5. A deleted id is never reused for a new card.
6. The canvas, sheet and summary panel drop the card live; event lines that name it still show the id as plain text.
7. The MCP instructions, the tool's description and SPILL.md say: never delete without the question; propose a delete only for a card that should not exist (a duplicate, or a change that belongs on an existing spec), not to undo the user's rejection.

## Out of scope
- Deleting from the app without a question (a delete button for the user).
- Undoing a delete.
- Done specs (spill_propose_replace covers them).

## Acceptance checks
1. On a board copy, spill_propose_delete on a draft spec opens the question; answering A removes the card, its links and its blocking-only questions, logs the event, and the inbox shows it.
2. Answering B leaves the card as it was.
3. Proposing a done, active or queued spec is refused.
4. A new spec after a delete gets the next id, not the deleted one.
